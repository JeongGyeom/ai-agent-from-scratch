# CH04 ELI5: 도구를 쓰는 AI 비서 만들기

원본: [ch04_react_agent.ipynb](./ch04_react_agent.ipynb)

ELI5는 “다섯 살 아이에게 설명하듯 쉽게 풀어 설명하기”라는 뜻입니다. 이 문서는 노트북의 4.1~4.8 흐름을 따라가며, 코드가 왜 필요한지부터 설명합니다.

## 1. 이 장에서 만드는 것

친구에게 “1234 × 5678이 얼마야?”라고 물었다고 해 봅시다.

친구는 계산기를 꺼내 숫자를 입력하고, 화면에 나온 값을 읽어 답할 수 있습니다. 이 장의 **에이전트(Agent)**도 비슷합니다. 언어 모델에게 질문만 던지는 데서 한 걸음 더 나아가, 모델이 요청한 도구를 실행하고 그 결과를 다시 알려 줍니다.

등장인물을 먼저 구분하면 이해하기 쉽습니다.

| 코드 이름 | 쉬운 비유 | 맡은 일 |
|---|---|---|
| LLM | 다음 행동을 고르는 친구 | 바로 답할지, 도구를 요청할지 결정 |
| `Agent` | 일을 진행하는 담당자 | 모델 호출, 도구 실행, 기록, 종료를 조율 |
| `BaseTool` / `FunctionTool` | 계산기나 검색 도구 | 요청받은 실제 작업 수행 |
| `ExecutionContext` | 작업 수첩 | 질문, 요청, 결과, 진행 상태 보관 |
| `LlmClient` | 통역사 | 내부 자료와 모델 API의 자료 형식을 서로 변환 |

**모델이 “계산기를 써 줘”라고 요청하면, 실제 계산기를 실행하는 쪽은 파이썬 프로그램입니다.**

## 2. 4.1 — ReAct: 생각하고, 행동하고, 결과 보기

ReAct는 Reasoning과 Acting을 연결한 이름입니다. 여기서는 “다음 행동 결정 → 도구 실행 → 결과 확인”을 반복하는 구조로 이해하면 됩니다.

```text
사용자 질문
    ↓
모델에게 지금까지의 기록과 도구 목록 전달
    ↓
모델의 응답
    ├─ 도구 요청 → 파이썬이 실행 → 결과를 수첩에 기록 ─┐
    │                                                │
    │                    다음 모델 호출로 돌아가기 ←─┘
    └─ 최종 답변 → 사용자에게 반환
```

예를 들어 계산 도구를 선택했다면 다음처럼 진행할 수 있습니다.

1. 사용자: “1234 × 5678은?”
2. 모델: “`calculator`로 두 수를 곱해 줘.”
3. 프로그램: 계산기를 실행해 `7006652`를 얻고 기록합니다.
4. 모델: 기록에 추가된 계산 결과를 보고 답합니다.
5. 프로그램: 최종 답변을 반환합니다.

이것은 설명을 위한 흐름입니다. 실제 모델은 도구 없이 바로 답할 수도 있습니다. 도구를 등록했다고 매번 쓰는 것은 아닙니다.

또한 `think()`는 모델 API를 호출하는 메서드 이름입니다. 모델의 머릿속 생각을 전부 출력하거나 저장한다는 뜻은 아닙니다.

## 3. 4.2 — 완성된 에이전트 사용하기

Listing 4.1의 사용법은 세 가지 준비물을 묶는 것입니다.

```python
agent = Agent(
    model=LlmClient(model="gpt-5.4-mini"),
    tools=[calculator, search_web],
    instructions="You are a helpful assistant"
)

result = await agent.run("What is 1234 * 5678?")
```

- `model`: 누구에게 다음 행동을 물어볼지 정합니다. 모델 이름은 노트북의 예시 설정입니다.
- `tools`: 사용할 수 있는 도구를 정합니다.
- `instructions`: 일을 처리할 때 따를 기본 지침을 줍니다.

`await`는 계산이나 통신이 끝날 때까지 이 작업의 진행을 기다린다는 뜻입니다. 기다리는 동안 다른 비동기 작업이 진행될 수 있지만, 이 장의 도구 실행이 모두 자동으로 병렬 처리되는 것은 아닙니다.

반환된 `result.output`에는 최종 답이, `result.context`에는 실행 기록과 상태가 들어갑니다.

## 4. 4.3 — ExecutionContext: 잊어버리지 않도록 적는 수첩

계산 결과를 받아 놓고 다음 모델 호출에 보여 주지 않으면, 모델은 그 결과를 활용할 수 없습니다. 그래서 실행 중 생기는 일을 기록합니다.

### 수첩에 들어가는 세 종류의 내용

| 자료형 | 뜻 | 예시 |
|---|---|---|
| `Message` | 사람이 읽는 말 | 사용자 질문, 모델의 답변 |
| `ToolCall` | 도구 실행 요청 | 계산기에 곱셈 요청 |
| `ToolResult` | 도구 실행 결과 | 계산값 또는 오류 메시지 |

`ToolCall`과 `ToolResult`에는 같은 `tool_call_id`를 붙입니다. 음식 주문서와 영수증에 같은 주문 번호를 적는 것처럼, **어떤 요청에 대한 결과인지 연결하기 위해서**입니다.

`ContentItem`은 이 세 가지 중 하나를 담을 수 있다는 타입 이름입니다.

### Event와 ExecutionContext의 차이

`Event`는 수첩에 붙이는 기록 한 장입니다. 기록 ID, 실행 ID, 시각, 작성자, 내용 목록을 담습니다. 하나의 이벤트에 여러 도구 요청이나 여러 결과가 들어갈 수도 있습니다.

`ExecutionContext`는 그 기록들을 모아 둔 수첩 전체입니다.

| 필드 | 쉬운 설명 |
|---|---|
| `execution_id` | 이번 작업의 번호 |
| `events` | 지금까지 쌓인 기록 |
| `current_step` | 몇 번째 반복까지 진행했는지 |
| `state` | 작업 중 따로 보관할 값 |
| `final_result` | 최종 답변. 아직 없으면 `None` |

`add_event()`는 기록을 붙이고, `increment_step()`은 반복 횟수를 하나 늘립니다. `state`를 포함한 수첩 전체가 모델에게 자동으로 전달되지는 않습니다. 이 장의 요청 생성 코드는 주로 `events` 안의 내용을 모아 보냅니다.

## 5. 4.4 — 도구마다 같은 사용 버튼 붙이기

계산기는 파이썬 함수이고, 검색 도구는 외부 서버에 있을 수 있습니다. 에이전트가 도구마다 사용법을 따로 알아야 한다면 코드가 복잡해집니다.

그래서 모든 도구에 **같은 모양의 사용 버튼**을 붙입니다.

### BaseTool: 도구가 갖춰야 할 약속

`BaseTool`은 도구의 공통 틀입니다.

- `name`: 도구를 찾는 이름.
- `description`: 어떤 일을 하는지 적은 설명.
- `tool_definition`: 모델에게 보여 줄 사용 설명서. 필요한 입력의 형태도 담습니다.
- `execute(context, **kwargs)`: 실제로 일을 하는 메서드.

`__call__()`도 정의되어 있어서 `await tool(context, **arguments)`처럼 도구를 함수처럼 부를 수 있습니다. 내부에서는 `execute()`가 실행됩니다.

### FunctionTool: 평범한 함수에 도구 포장 씌우기

`FunctionTool`은 기존 파이썬 함수를 위 약속에 맞게 감쌉니다.

1. 함수 이름과 설명을 읽습니다.
2. 매개변수와 타입 정보를 바탕으로 입력 설명서를 만듭니다.
3. 함수가 `context` 매개변수를 받으면 작업 수첩도 전달합니다.
4. 함수가 비동기 결과를 반환하면 `await`로 기다립니다.

`**kwargs`는 이름표가 붙은 입력 묶음을 풀어 전달하는 문법입니다. 예를 들어 `{"first_number": 1234}`를 `first_number=1234`처럼 넘깁니다.

### MCP: 다른 곳의 도구도 연결하기

MCP는 외부 프로그램의 도구를 정해진 방식으로 발견하고 호출하게 해 주는 연결 규약입니다. “다른 가게의 도구도 우리 작업대에서 쓸 수 있게 연결한다”고 생각하면 됩니다.

- `load_mcp_tools()`: 서버에 연결하고 초기화한 뒤 도구 목록을 가져옵니다.
- `_create_mcp_tool()`: 각 외부 도구를 `FunctionTool`로 감쌉니다.
- 감싼 함수가 호출되면 서버에 실제 실행 요청을 보내고 결과의 텍스트를 추출합니다.

노트북의 구현은 도구 목록을 읽는 연결과 실제 도구 호출 연결을 각각 엽니다. 외부 도구도 에이전트 입장에서는 같은 방식으로 호출할 수 있게 만드는 것이 핵심입니다.

## 6. 4.5 — LLM 통신 계층: 모델과 주고받는 편지

내부 코드가 쓰는 자료형과 모델 API가 요구하는 자료 형식은 다를 수 있습니다. 통신 계층이 중간에서 번역합니다.

```text
작업 수첩 → LlmRequest → LlmClient → 모델 API
작업 수첩 ← LlmResponse ← LlmClient ← 모델 응답
```

| 구성 요소 | 편지 비유 | 담는 것 또는 하는 일 |
|---|---|---|
| `LlmRequest` | 보내는 편지 | 지침, 대화 기록, 도구 목록, 도구 선택 정책 |
| `LlmClient` | 번역과 배송 담당 | API 형식 변환, LiteLLM 호출, 응답 해석 |
| `LlmResponse` | 받은 편지 | 메시지와 도구 요청, 오류 정보, 토큰 사용량 |

`_build_messages()`는 `Message`, `ToolCall`, `ToolResult`를 API 메시지 형식으로 바꿉니다. 이때 도구 요청의 인자는 JSON 문자열로 바꾸고, 도구 결과에는 요청 번호를 붙입니다.

`_parse_response()`는 반대로 API 응답을 내부의 `Message`와 `ToolCall`로 바꿉니다. 토큰 사용량은 요청과 응답에 사용된 텍스트 분량을 파악하는 자료입니다.

이 계층을 두면 에이전트의 반복 로직이 API 응답의 세부 구조를 직접 다루지 않아도 됩니다.

## 7. 4.6 — Agent: 모든 부품을 움직이는 담당자

메서드 이름을 다음처럼 읽으면 됩니다.

| 메서드 | 하는 일 |
|---|---|
| `run()` | 질문을 기록하고 끝날 때까지 반복 |
| `step()` | 모델 호출과 필요한 도구 실행을 한 차례 진행 |
| `_prepare_llm_request()` | 기록에서 모델에게 보낼 자료 준비 |
| `think()` | 모델에게 다음 응답 요청 |
| `act()` | 요청된 도구 실행 |
| `_is_final_response()` | 종료 조건 확인 |
| `_extract_final_result()` | 종료 이벤트에서 답 꺼내기 |

### 한 바퀴가 도는 순서

```text
step(context)
  1. events의 내용 목록을 하나로 모아 LlmRequest 만들기
  2. think(): 모델 호출
  3. 모델 응답을 Event로 기록
  4. ToolCall이 있으면 act()로 실행하고 결과 기록
  5. current_step을 1 증가
```

한 `step`에서 여러 도구를 요청받을 수 있습니다. 따라서 `current_step`은 도구 호출 횟수와 같지 않습니다. 이 장의 `act()`는 요청 목록을 `for`문으로 순서대로 실행합니다.

### 언제 멈출까?

일반 텍스트 모드에서는 마지막 이벤트에 `ToolCall`도 `ToolResult`도 없으면 최종 응답으로 판단하고, 그 안의 assistant 메시지를 꺼냅니다. 이는 “답이 사실인지 검사했다”는 뜻이 아니라, 코드가 정한 종료 규칙입니다.

`max_steps`는 계속 도구만 부르는 상황을 막기 위한 반복 한도입니다. 기본값은 10입니다. 한도에 닿아 멈췄다고 최종 답이 생기는 것은 아니므로, `result.output`이 `None`일 수 있습니다.

### 도구가 실패하면?

도구를 찾을 수 없거나 실행 중 예외가 나면 `status="error"`인 `ToolResult`를 기록합니다. 다음 호출에서 모델은 그 오류를 보고 다른 입력이나 행동을 선택할 수 있습니다. 성공적인 복구를 보장하는 것은 아닙니다.

## 8. 4.7 — 구조화된 출력: 답변을 정해진 양식에 담기

“이 상품평은 긍정적인 것 같아요”라는 문장은 사람이 읽기 좋습니다. 하지만 프로그램이 결과를 쓰려면 항목이 정해진 양식이 편리합니다.

노트북은 다음 Pydantic 모델을 사용합니다.

```python
class SentimentAnalysis(BaseModel):
    sentiment: Literal["positive", "negative", "neutral"]
    confidence: float
    key_phrases: List[str]
```

이것은 “감정, 확신도, 핵심 표현을 이 칸에 써 줘”라는 답안지입니다.

`output_type=SentimentAnalysis`를 지정하면 에이전트는 `final_answer`라는 특별한 도구를 추가합니다. 이 도구는 외부 정보를 찾기 위한 것이 아니라 **완성된 답을 제출하는 창구**입니다.

1. 원하는 출력 형식으로 `final_answer` 도구 설명서를 만듭니다.
2. 모델이 도구를 사용하도록 `tool_choice="required"`를 설정합니다.
3. 모델이 `final_answer`를 호출하면 입력을 출력 모델로 변환·검증합니다.
4. 해당 도구가 성공한 결과를 발견하면 반복을 끝냅니다.
5. 결과 객체를 `result.output`으로 돌려줍니다.

`required`는 “반드시 어떤 도구를 호출하라”는 뜻입니다. 검색 도구도 등록되어 있다면 검색을 먼저 쓸 수 있으므로, 첫 응답부터 `final_answer`만 호출하도록 강제하는 설정은 아닙니다.

출력 예시의 `confidence=0.92` 같은 값은 모델이 내놓는 값입니다. 실제 정확도가 92%라고 측정됐다는 뜻은 아닙니다. 또한 이 예제의 `float` 선언 자체에는 0~1 범위 제한이 없습니다.

## 9. 4.8 — GAIA: 실제 문제로 연습시키기

앞부분이 비서 만들기였다면, 이 부분은 만든 비서에게 시험 문제를 주는 과정입니다.

노트북은 다음 순서로 실험합니다.

1. GAIA의 `2023_level1` validation 데이터를 불러옵니다.
2. 그중 처음 10개 문제를 고릅니다.
3. Tavily MCP 서버에서 검색 관련 도구를 가져옵니다.
4. `GaiaOutput` 형식으로 답하도록 에이전트를 구성합니다.
5. `run_experiment(..., tools=mcp_tools)`로 문제를 풀고 결과를 모읍니다.

`GaiaOutput`에는 풀 수 있는지 나타내는 `is_solvable`, 풀 수 없는 이유인 `unsolvable_reason`, 최종 답인 `final_answer`가 있습니다. GAIA용 에이전트의 반복 한도는 15입니다.

여기서 코드 연결을 읽을 때 구분할 부분이 있습니다. 노트북의 `Semaphore(3)`은 그 아래 정의한 `solve_problem()`을 통해 실행하는 작업의 동시 진행 수를 제한합니다. 뒤의 `run_experiment()`는 패키지 내부의 평가 함수를 사용하므로, 그 실험 전체가 이 지역 세마포어로 3개씩 제한된다고 읽으면 안 됩니다.

노트북에는 실험을 실행하는 코드가 있지만 저장된 실행 출력은 없습니다. 따라서 이 파일만으로 정답률이나 특정 모델의 성능을 알 수는 없습니다.

### display_trace(): 답이 나온 경로 따라가기

마지막 예제는 마라톤 속도로 달까지 가는 시간을 묻고 `display_trace(result.context)`를 실행합니다.

실행 기록을 보면 어떤 도구를 요청했는지, 무엇을 반환했는지, 오류가 있었는지 확인할 수 있습니다. 답이 이상할 때 검색 결과, 단위 변환, 계산 중 어느 부분을 살펴봐야 할지 찾는 데 도움이 됩니다. 이 기록은 프로그램에 남은 메시지와 도구 활동이며, 모델 내부 사고 전체를 보여 주는 자료는 아닙니다.

## 10. 노트북을 읽거나 실행할 때 알아둘 점

- 위에서 아래로 코드를 실행합니다. 첫 셀은 저장소 위치를 찾고 `.env`를 읽으며 프로젝트 패키지를 가져옵니다.
- **Implementation excerpt** 표시가 있는 코드는 설명용 마크다운 코드 조각입니다. 그 셀을 실행해도 클래스가 정의되는 것은 아닙니다.
- 실제 통합 예제의 `from scratch_agents import Agent`는 저장소의 완성된 패키지를 사용합니다. CH04 시점의 구조를 비교하려면 같은 폴더의 [agent.py](./agent.py), [base.py](./base.py), [context.py](./context.py)를 함께 읽으면 됩니다.
- 설명용 Listing 4.20에서는 `step()`이 도구 결과 이벤트를 기록하지만, CH04의 `agent.py`에서는 `act()` 안에서 기록합니다. 둘 다 도구 결과를 다음 모델 호출에 전달하려는 구조입니다. 두 버전을 섞어 그대로 붙여 넣으면 안 됩니다.
- 실행 준비는 [루트 README](../../README.md)를 따릅니다. CH04 전체 실행에는 모델 API 접근 외에도 Tavily 키, Node.js/npm의 `npx`, GAIA 데이터 접근 준비가 필요합니다. API 호출에는 비용이 발생할 수 있습니다.

## 11. 이해했는지 확인하기

**Q. 모델이 계산기를 직접 실행하나요?**  
A. 모델은 이름과 입력을 담은 요청을 만들고, 파이썬의 `act()`가 도구를 실행합니다.

**Q. 계산 결과는 어떻게 다음 모델 호출에 전달되나요?**  
A. `ToolResult`를 이벤트에 기록하고, 다음 `LlmRequest`를 만들 때 기록의 내용을 모아 보냅니다.

**Q. `run()`과 `step()`은 어떻게 다른가요?**  
A. `step()`은 한 바퀴이고, `run()`은 종료 조건이나 반복 한도에 도달할 때까지 그 바퀴를 돌립니다.

**Q. `final_answer`는 왜 도구인가요?**  
A. 모델이 이미 사용하는 도구 호출 형식을 이용해, 정해진 양식의 답을 제출하게 만들기 위해서입니다.
