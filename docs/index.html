AutoGPT와 BabyAGI

높은 자율성의 가능성, 그리고 긴 작업의 불안정성

“LLM에게 모든 실행 판단을 맡겨도 될까?”

출처 / 설명 · AutoGPT · BabyAGI · IBM · IBM
약 2분. 2023년 봄 AutoGPT와 BabyAGI가 목표 기반 실행 실험을 대중화했습니다. GPT-4가 상징적이지만 초기 BabyAGI는 GPT-3.5 기본 설정도 사용했으므로 두 프로젝트 모두 GPT-4 전용이었다고 설명하면 안 됩니다. AutoGPT의 도구 실행 루프와 BabyAGI의 작업 실행·생성·우선순위 큐는 서로 다른 구현입니다. 그림은 공통 아이디어를 단순화한 것으로 원본의 동일한 제어 흐름이 아닙니다. 오류 누적과 환각, 상태 관리의 한계는 긴 자율 실행의 설계 위험이지, 이 프로젝트들에 메모리나 제어 장치가 전혀 없었다는 뜻은 아닙니다.

02 / 2024

Agentic Workflow와 LangGraph

복잡한 작업을 단계로 나누고, 상태와 전이를 명시한다

Workflow와 Agent는 자율성을 어디에 둘지 정하는 설계 방식

출처 / 설명 · LangGraph · Andrew Ng
약 2분. Andrew Ng는 2024년 3~4월 Reflection, Tool Use, Planning, Multi-agent collaboration을 설명했습니다. 이 패턴 자체를 그때 발명했다는 뜻은 아닙니다. LangGraph의 공식 소개 글은 2024년 1월 17일이며 상태와 순환 그래프를 강조합니다. Node는 모델 호출 또는 일반 함수가 될 수 있습니다. Edge는 다음 실행 위치를 연결하고 State는 노드 사이에서 갱신되는 정보입니다. 그림의 Planner/Executor/Verifier는 교육용 설계 예시입니다. 개발자는 전이 규칙과 검증 기준을 결정론적으로 정의할 수 있지만, LLM을 포함한 전체 실행 결과가 결정론적이라는 뜻은 아닙니다. Workflow 내부에 Agent Loop를 넣거나 모델이 라우팅을 고르게 할 수 있습니다.

FOUNDATION / ReAct

ReAct와 Agent Loop

다음 행동은 고정된 대본이 아니라, 관측 결과에 따라 달라진다

루프는 오래된 아이디어다. 모델의 도구 사용 능력이 실용성을 높였다.

출처 / 설명 · ReAct · LangChain
약 1분 30초. ReAct의 arXiv 최초 제출은 2022년 10월 6일이고 ICLR 2023 논문입니다. 2025년에 새로 등장한 기법이 아닙니다. 추론과 행동을 교차시키고 외부 관측을 받아 계획을 수정하는 원리를 보세요. 그림은 개념적 루프이며 현대 에이전트가 내부 추론을 모두 사용자에게 노출해야 한다는 의미가 아닙니다. 모든 도구 호출 루프가 원 논문의 프롬프팅을 그대로 구현하는 것도 아닙니다. 최근 모델의 안정적인 도구 사용이 단순한 루프의 활용 범위를 넓혔다는 것은 설계적 해석이며, 이 발표에서는 모델 간 정량 성능 비교를 주장하지 않습니다.

IMPLEMENTATION / mini-swe-agent

단순한 코드, 명시적인 실행 경계

실제 구현 · 문서의 DefaultAgent 제어 흐름을 요약

agent.py · 실제 핵심 코드
def step(self):
    return self.execute_actions(self.query())

query() 다음 행동 생성
execute_actions() 실행 + 관측 추가
run() 종료할 때까지 반복

에이전트 루프는 단순하다. 안정성은 실행 환경과 제어 장치에서 나온다.

출처 / 설명 · mini-swe-agent
약 2분. 왼쪽은 공식 문서의 step 메서드와 같은 호출 구조입니다. 줄바꿈만 발표용으로 바꿨습니다. query는 한도를 검사하고 모델 응답을 메시지에 추가합니다. execute_actions는 환경 실행과 관측 메시지 추가를 담당합니다. run은 초기화한 뒤 반복하며 종료 신호를 만나면 결과를 반환합니다. 우측은 세부 처리를 합친 요약도입니다. 모든 예외가 재시도되는 것은 아닙니다. 복구 가능한 InterruptAgentFlow 계열은 피드백으로 처리하고, 그 외 예외는 다시 전파될 수 있습니다. 비용 및 스텝·시간 제한의 정확한 동작은 버전에 따라 다르며 일부 검사는 호출 전 누적 비용을 기준으로 하므로 한 번의 호출로 예산을 초과할 수도 있습니다. 모델이 제출했다고 해서 코드가 올바르다고 검증된 것은 아닙니다.

PROTOCOL / TOOL CALLING

도구를 요청하는 모델, 실행하는 Runtime

Sequence Diagram · Runtime이 관리하는 Client Tool 기준

LLM은 도구 실행을 요청하고, 실제 실행은 Runtime이 담당한다.

출처 / 설명 · Claude Docs
약 2분. 위에서 아래로 시간을 읽습니다. 사용자 목표를 받은 Runtime이 Context와 도구 스키마를 보냅니다. LLM 출력의 Tool Call은 함수 이름과 인자이며 실행 그 자체가 아닙니다. Runtime은 스키마·권한·허용 정책을 확인하고 실제 도구를 실행한 뒤 도구 결과를 대화에 추가합니다. 그 결과를 다시 모델에게 보내 다음 호출 또는 최종 응답을 받습니다. 인자 유효성은 의미적으로 안전하거나 목표가 달성됐다는 보장이 아니므로 실행 후 검증도 필요합니다. 이것은 개발자 측 client tool 흐름입니다. 제공자 측 server tool은 제공자 인프라가 실행을 맡을 수 있지만 모델이 요청하고 실행 계층이 수행한다는 구분은 같습니다.

CASE STUDY / POKÉMON RED

성공 판정은 게임 상태가 한다

포켓몬 레드 + PyBoy · 요청된 아키텍처를 바탕으로 한 구현 설계 예시

모델의 판단보다 실제 환경 상태와 검증 결과를 우선한다.

출처 / 설명 · PyBoy · pret/pokered
약 2분 30초. 특정 공개 프로젝트의 검증된 실적이나 동일한 구조를 주장하는 사례가 아닙니다. 사용자 요청의 역할 분리를 PyBoy로 구현하는 설계 예시입니다. PyBoy는 버튼 입력과 메모리 접근을 제공하고, Pokémon Red의 RAM 심볼은 pret/pokered 역공학 자료로 확인할 수 있습니다. 먼저 목표와 관측 상태를 Planner에 주고, Python Executor가 버튼을 누르고 프레임을 진행합니다. Verifier는 전후의 파티 수, 종 데이터, 획득 플래그 등 목표에 필요한 신호를 확인합니다. 선택 화면만 열리고 파티 데이터가 그대로라면 성공으로 판정하지 않습니다. 실제로는 파티가 꽉 찬 경우 등도 있어 목표별 사후 조건을 정의해야 합니다. 주소와 오프셋은 ROM 버전에 맞춰 확인해야 하며, 한 바이트 변화만으로 일반화하지 않습니다. Interpreter는 검증 결과를 해석해 목표와 기억을 갱신하고 Coordinator가 재시도·종료를 통제합니다.

03 / 2025

Context Engineering

프롬프트 문구를 넘어, 에이전트의 정보 흐름을 설계한다

무엇을 기억하고, 무엇을 보여주고, 무엇을 분리할 것인가?

출처 / 설명 · LangChain
약 2분. LangChain의 2025년 7월 글은 기존의 여러 기법을 Write, Select, Compress, Isolate의 네 범주로 정리합니다. 이 해에 메모리나 RAG가 처음 생긴 것은 아닙니다. Write는 창 밖에 정보를 저장하는 것이고 Select는 다음 호출에 필요한 것을 다시 가져오는 것입니다. RAG, Memory Retrieval, Tool Search는 선택 수단입니다. Compress는 요약과 도구 결과 축약으로 창을 줄이지만 원문과 검증 근거를 잃지 않도록 해야 합니다. Isolate는 역할별 또는 Subagent별 문맥을 분리하고 필요한 결과만 회수하는 방식입니다. 반드시 여러 에이전트를 써야 한다는 뜻은 아닙니다. Context Window가 커져도 비용·지연과 불필요한 정보의 혼입 문제가 사라지는 것은 아닙니다.

04 / 2026

Agent Harness

LLM을 둘러싼 실행·제어 시스템

모델이 작동하는 환경의 품질이, Agent의 신뢰성을 좌우한다.

출처 / 설명 · OpenAI · LangGraph
약 2분. Harness는 모델을 감싸고 실행을 조직하는 소프트웨어와 환경을 가리키는 넓은 용어입니다. 이 그림은 발표를 위한 종합 분류이며 업계의 단일 표준이나 OpenAI 글의 고유 구성도는 아닙니다. 2026년에 처음 발명된 기술이라고 말하면 안 됩니다. LangGraph나 이전 런타임도 제어·상태·메모리를 제공했습니다. 2026년 2월 11일 OpenAI의 글은 에이전트가 읽을 수 있는 저장소 지식, 제약을 강제하는 도구, 관측 가능성과 피드백 루프의 중요성을 보여줍니다. Harness Engineering의 범위는 이 런타임 도식보다 넓어 저장소 구성과 개발 환경도 포함할 수 있습니다. 핵심은 더 강한 모델을 기다리는 것과 함께 환경 자체를 개선하는 것입니다.

SYNTHESIS / ARCHITECTURE

자율성의 배치와 통제 범위

세 구조의 전형적 모습 · 경계와 역할을 단순화한 비교

진화는 교체가 아니라 결합이다. Workflow도 Harness 안에서 실행된다.

출처 / 설명 · LangGraph · OpenAI
약 2분. 왼쪽도 도구를 실행하는 Runtime이 있습니다. 초기 시스템에 제어가 전혀 없었다는 비교가 아닙니다. 보라색은 모델 판단이고 청록색은 개발자가 정의한 실행·제어 영역입니다. 가운데는 계획과 실행, 검증을 명시적으로 나누며 검증이나 라우팅에도 필요하면 모델을 넣을 수 있습니다. 오른쪽은 그 루프와 Workflow를 Context, State, 검증 및 복구와 함께 운영합니다. 이 세 가지는 배타적인 제품 분류가 아니며 실제 구현은 섞입니다. 모든 상황에서 가장 복잡한 Harness가 최선이라는 뜻도 아닙니다. 필요한 자율성과 실패 비용에 맞춰 통제 수준을 선택합니다.

TAKEAWAY / FIVE PRINCIPLES

좋은 Agent를 만드는 다섯 가지 원칙

관측에서 갱신까지, 루프 전체를 설계한다

모델 성능만큼, 제어와 검증 시스템의 품질을 높이자.

출처 / 설명 · 발표 요약 · Observe → Decide → Execute → Verify → Update
약 1분. 다섯 단계를 다시 강조합니다. Observe에서는 실제 환경 상태를 가져오고 Decide에서 모델이 다음 행동을 제안합니다. Execute에서는 Runtime이 실행하며 Verify에서는 목표의 사후 조건을 확인합니다. Update는 검증된 결과를 바탕으로 목표와 기억을 수정합니다. 단계를 반드시 다섯 개의 별도 서비스로 나누라는 뜻은 아닙니다. 설계와 디버깅에서 책임을 빠뜨리지 않기 위한 원칙입니다. 마지막 문장: Agent는 답을 말하는 모델이 아니라, 환경에 행동하고 결과를 확인하며 다음 행동을 바꾸는 시스템입니다. 청중에게 자신의 Agent에서 성공을 누가 어떤 증거로 판정하는지 떠올려 보도록 마무리합니다.
